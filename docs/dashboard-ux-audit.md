# Аудит и целевая модель дашборда ONEPAP.24 Modbus Configurator

Дата: 2026-08-03  
Объект: `configurator/ui`, `configurator/api`, `configurator/modbus`  
Статусы доказательности: **ПИ** — подтверждено интерфейсом; **ПК** — подтверждено кодом; **ПД** — подтверждено документацией; **UXГ** — UX-гипотеза; **ТП** — требует проверки на реальном контроллере.

## 1. Краткое понимание продукта

ONEPAP.24 Modbus Configurator — локальное сервисное веб-приложение для чтения и записи параметров 11 шагов окраски Папаниколау, настройки координат двух селекторов, запуска технологических программ, ручной проверки механизмов и диагностики контроллера по Modbus RTU. **ПД:** `ТЗ_Modbus_Configurator.md`; **ПК:** `configurator/api/server.go`, `configurator/modbus/operations.go`.

Главный объект продукта — не «аналитический дашборд», а **подключённый контроллер и выполняемая над ним безопасная операция**. Главный рабочий цикл: подключить → проверить готовность → прочитать фактические значения → изменить минимум необходимого → записать и подтвердить результат → при необходимости диагностировать ошибку.

## 2. Основные пользователи и их задачи

| Пользователь | Контекст | Цель | Основные действия | Частота | Риск ошибки |
|---|---|---|---|---:|---|
| Сервисный инженер | Пусконаладка, ремонт | Настроить и проверить аппарат | Подключение, координаты, тесты, диагностика | периодически | высокий |
| Инженер ПНР | Ввод в эксплуатацию | Подтвердить корректность механики и протокола | чтение/запись, селекторы, программы | сериями | высокий |
| Обученный лаборант | Эксплуатация | Проверить состояние и запустить штатный цикл | статус, чтение, полный цикл | ежедневно | средний/высокий |
| Разработчик/испытатель | Стенд | Найти дефект протокола или API | журнал, датчики, отдельные команды | нерегулярно | средний |

Пять главных сценариев: подключение; чтение и изменение протокола; запись координат; запуск полного цикла; диагностика и безопасное восстановление.

## 3. Карта текущего дашборда

| Раздел | Назначение | Целевая роль | Основные действия | Связи | Исходная проблема |
|---|---|---|---|---|---|
| Настройки | 11 шагов и порог реагента | инженер, лаборант | читать, менять, писать | диагностика | источник значений неочевиден |
| Клапаны | координаты селекторов | инженер | читать/писать 30 позиций | сервис | запись всех позиций вместо изменённых |
| Программы | технологические циклы | все роли | запуск, пауза, стоп | статус, журнал | штатные и опасные команды смешаны |
| Тестирование | входы и измерения | инженер | читать датчики | диагностика | свежесть данных не показана |
| Диагностика | ошибка и журнал | инженер | читать, сбрасывать, очищать | все разделы | слабая связь «ошибка → действие» |

Целевая глобальная навигация сохранена плоской: **Протокол окраски / Координаты клапанов / Программы и сервис / Датчики / Диагностика**. Сервисные операции раскрываются внутри раздела, а не конкурируют с ежедневными задачами.

## 4. Главный UX-вердикт

Исходный интерфейс визуально аккуратен, но организован как универсальный SaaS-dashboard: четыре равноправные KPI, карточная сетка программ и одинаковая заметность действий. Для аппаратного конфигуратора это ослабляет причинно-следственную связь и безопасность. **ПИ:** исходные `index.html`, `style.css`.

Сильнейшее улучшение — заменить обзорные KPI на постоянный контекст устройства: подключение, Ready, ошибка, свежесть данных, блок внимания и прогресс. Целевая версия отвечает на четыре вопроса: **к какому устройству подключён пользователь; можно ли действовать; откуда взяты значения; что будет записано или запущено**.

## 5. Критические проблемы

| Приоритет | Проблема | Доказательство | Эффект | Решение |
|---|---|---|---|---|
| P0 | API записывал все 11 шагов и 30 координат | **ПК:** `api/settings.go` | лишнее воздействие, долгие операции, риск частичной записи | фильтровать `Dirty`, очищать только успешно записанное |
| P1 | значения по умолчанию выглядели как фактические | **ПИ/ПК:** начальная отрисовка UI | ложное доверие | маркировать «не прочитано», показывать источник и время |
| P1 | опасные действия смешаны со штатными | **ПИ:** раздел программ | случайный запуск/сброс | отдельные сервисная и опасная зоны, подтверждения |
| P1 | `alert/confirm` и слабая модель ошибок | **ПК:** исходный `app.js` | непоследовательная обратная связь | единый modal/toast/live-region |
| P1 | локальная `replace` в `go.mod` | **ПК:** `configurator/go.mod` | невоспроизводимая сборка | использовать публичную зависимость без машинного пути |
| P2 | мобильная навигация исчезала | **ПИ:** CSS `#sidebar{display:none}` | разделы недоступны | нижняя навигация на узком экране |
| P2 | отсутствовал CI | **ПК:** дерево репозитория | регрессии не обнаруживаются | Go test/vet/format + Windows build |

## 6. Аудит главного экрана

| Блок | Назначение | Польза | Проблема исходной версии | Целевая версия | Приоритет |
|---|---|---|---|---|---|
| KPI ×4 | общий статус | низкая/средняя | «Шагов прочитано» и крупные числа занимают главный фокус | компактная строка Ready/Ошибка | P2 |
| Подключение | открыть COM-порт | высокая | спрятано в узкой верхней панели | самостоятельный device bar | P1 |
| Блок внимания | указать следующий шаг | отсутствовал | пользователь сам интерпретирует регистры | «не подключён / занят / ошибка / готов» | P1 |
| Таблица шагов | основная работа | высокая | источник и dirty-состояние недостаточно явны | источник, время, состояние строки, счётчик изменений | P1 |
| Прогресс | долгая операция | средняя | разрознен | глобальный live-progress | P1 |

Главное действие зависит от состояния: без соединения — **Подключить**; после соединения — **Прочитать из контроллера**; после изменения — **Записать изменения**. Одновременной конкуренции трёх CTA нет.

## 7. Аудит навигации

Исходные названия «Настройки» и «Клапаны» были слишком общими. Целевые названия содержат объект. Текущее положение обозначается `aria-current`, URL hash сохраняет раздел, на мобильном навигация остаётся доступной. Глубокая вложенность не нужна: продукт имеет пять устойчивых областей.

| Элемент | Проблема | Последствие | Рекомендация |
|---|---|---|---|
| «Настройки» | неясный объект | поиск раздела по памяти | «Протокол окраски» |
| «Клапаны» | неясно: тест или координаты | риск неверного раздела | «Координаты клапанов» |
| «Программы» | смешение штатного и сервиса | опасные команды заметны как обычные | «Программы и сервис», сервис скрыт в disclosure |
| Мобильная версия | sidebar исчезал | потеря навигации | фиксированная нижняя панель |
| Контекст | нет стабильного источника/свежести | пользователь не знает актуальность | статус телеметрии и время чтения |

## 8. Аудит информационной иерархии

Первый визуальный уровень: состояние устройства и системное предупреждение. Второй: заголовок текущей задачи и основной CTA. Третий: рабочие данные. Четвёртый: сервисные и опасные операции. Цвет используется семантически: синий — основное действие; жёлтый — несохранённое; красный — ошибка/разрушительное; зелёный — подтверждённое состояние. Карточки оставлены только как границы самостоятельных рабочих областей; декоративная сетка KPI удалена.

## 10. Аудит ключевых сценариев

| Сценарий | Исходные шаги | Проблема | Целевой flow | Риск после изменения |
|---|---:|---|---|---|
| Подключение | 1 экран, 3 поля | ошибка конкурировала с панелью | параметры → подключить → готов/ошибка → доступные действия | низкий |
| Изменить шаг | чтение не обязательно визуально | можно принять default за device data | подключить → прочитать → изменить → увидеть dirty → подтвердить → записать | средний |
| Изменить координату | записывались все 30 | лишние Modbus-операции | прочитать → изменить позиции → счётчик → записать только dirty | средний |
| Полный цикл | одна из равных карточек | неясен главный сценарий | готовность → проверки → подтверждение → запуск → прогресс → результат | средний |
| Сброс ошибки | контекст слаб | сброс без устранения причины | открыть диагностику → сохранить код → устранить → подтвердить сброс → повторно проверить | средний |

Критерий завершения любой записи: сервер вернул успех, dirty-флаги сняты только у переданных объектов, UI показал количество записанного. При ошибке интерфейс предупреждает о возможной частичной записи и не выдаёт ложный success.

## 11. Аудит форм и таблиц

Поля соединения сгруппированы в одну форму; числовые диапазоны заданы HTML и повторно проверяются в JS/API. Таблицы сохраняются таблицами: строка соответствует шагу/позиции, sticky header, горизонтальный scroll на узком экране. Обязательные колонки протокола: шаг, реагент, экспозиция, налив, состояние. Для клапанов: позиция, назначение, координата, состояние. Массовое действие одно — записать изменённые строки; отдельные чекбоксы не нужны, потому что набор вычисляется автоматически.

## 14. Аудит доступности

Реализованы semantic buttons вместо ссылок без `href`; `label` для соединения; `scope=col`; skip-link; `aria-current`; live-region; `role=alertdialog`; явный focus-visible; управление Escape; reduced-motion; forced-colors; цвет не является единственным носителем состояния. **ТП:** необходим ручной проход NVDA + Firefox/Chrome и проверка focus trap в модалях. P1-остаток: полноценный focus trap и возврат фокуса инициатору.

## 15. Аудит адаптивности

Desktop: постоянная боковая навигация, две таблицы клапанов, двухколоночные программы. Узкий desktop/tablet: свёрнутая навигация, один столбец сложных блоков. Mobile: нижняя навигация, connection form в один/два столбца, таблицы с горизонтальным scroll; опасные операции доступны, но не доминируют. Полная настройка 30 координат на телефоне допустима только как аварийный сценарий; основной целевой viewport — ноутбук сервисного инженера.
