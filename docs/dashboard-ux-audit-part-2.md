# Аудит ONEPAP.24 — часть 2

Продолжение [части 1](dashboard-ux-audit.md).

## 17. Признаки нейрослопа

| Элемент | Признак | Почему мешал | Замена |
|---|---|---|---|
| 4 KPI-карточки | шаблонная dashboard-сетка | нет решений, равный вес | строка состояния устройства |
| карточки всех программ | одинаковый приоритет | штатный и сервисный сценарий не различаются | primary full-cycle + command list |
| декоративные символы/emoji | иконка без функции | визуальный шум, неодинаковый рендеринг | текстовые коды и семантические статусы |
| крупные числа Ready/Error | псевдоаналитика | регистры не KPI | компактные диагностические значения |
| одинаковые панели | отсутствие иерархии | опасные действия выглядят обычными | service/details и danger-zone |
| общие глаголы | слабый объект действия | неясны последствия | «прочитать из…», «записать…», «сбросить…» |

## 18. Что нужно удалить или упростить

Удалить KPI «Шагов прочитано» как постоянную метрику; убрать декоративную ромбовидную иконку и emoji; не показывать все программы карточками; не отправлять неизменённые настройки; не скрывать навигацию на мобильном; не использовать системные `alert/confirm`; не считать default-значения подтверждёнными устройством.

## 19. Что нужно сохранить

Сохранить тёмную профессиональную тему, нулевые радиусы, плотные таблицы, mono для регистров/координат, плоскую IA из пяти разделов, SSE/WebSocket-подобную realtime-модель, явную аварийную кнопку, раздельное управление окраской и подробный журнал.

## 20. Каких функций не хватает

P1: серверный read-only режим роли лаборанта; журнал аудита «кто/когда/старое/новое»; проверка версии/идентификатора контроллера перед записью; повторное чтение и сравнение после записи. P2: экспорт диагностического пакета; сохранение/загрузка профиля с diff-preview; индикатор stale data; отмена/сворачивание долгой операции при поддержке backend. Все пункты — **продуктовые гипотезы**, пока не подтверждены пользовательскими данными.

## 21. Целевая структура дашборда


## 22. Целевые пользовательские сценарии

**Настройка протокола:** подключение → Ready=0 → прочитать 11 шагов → показать источник → изменить поля → локальная валидация → счётчик dirty → подтверждение → PUT изменённых объектов → Modbus запись dirty-only → результат → повторное чтение как будущая P1-проверка.

**Полный цикл:** подключение → блок внимания «готов» → открыть программы → проверить предусловия → подтвердить → запустить → видеть шаг/прогресс → при reagent-low выбрать конкретное действие → получить итог/ошибку → перейти в диагностику.

**Диагностика:** увидеть системную ошибку → открыть раздел → скопировать код/контекст → устранить причину → подтвердить сброс → автоматически обновить статус.

## 23. Новые тексты интерфейса

Ключевые тексты внедрены в `index.html`: «Контроллер не подключён», «Контроллер занят», «Контроллер готов», «Данные контроллера не прочитаны», «Показаны значения по умолчанию, не подтверждённые контроллером», «Записать изменения», «Частичная запись возможна», «Опасная зона». Тексты описывают состояние, объект и последствия без маркетинговой воды.

## 24. Рекомендации по дизайн-системе

Один spacing scale 4/8/12/16/24; три уровня поверхности; один accent; семантические success/warning/danger; radius=0; один primary CTA на рабочую область; secondary для безопасных альтернатив; danger только для остановки/сброса; таблица — для однотипных параметров; command-list — для операций; `details` — для редкого сервиса; state-label — для происхождения/состояния, не для украшения.

## 26. План пользовательского тестирования

1. Пять сервисных инженеров/ПНР: подключить устройство, изменить один шаг, объяснить что будет записано. Успех: 5/5 понимают источник и dirty-only без подсказки.  
2. Пять пользователей: найти полный цикл и запустить до подтверждения. Успех: first-click ≥80%, опасный сброс никто не выбирает.  
3. Error-recovery: показать код ошибки, найти диагностику и описать безопасный следующий шаг. Успех: completion ≥80%, нулевой случайный reset.  
4. Keyboard/NVDA: навигация, таблица, modal, toast. Успех: нет блокирующих WCAG-проблем.  
5. Стенд с контроллером: частичный сбой на записи. Успех: UI не показывает полный успех, незаписанные dirty остаются.

## 27. Метрики успеха

| Метрика | Где собирать | Цель | Ограничение |
|---|---|---|---|
| time to ready context | connect → Ready shown | <2 с после ответа API | зависит от Modbus |
| task completion: один шаг | с чтения до подтверждения | ≥90% | нужен стенд |
| unintended writes | число записей неизменённых объектов | 0 | логировать backend |
| time on task | изменение одного шага | −30% от baseline | baseline отсутствует |
| error recovery rate | ошибка → корректное действие | ≥80% | сценарии должны быть реалистичны |
| destructive cancel rate | отмена подтверждений | наблюдать, не оптимизировать вниз | высокая может означать спасённые ошибки |
| accessibility blockers | ручной/E2E аудит | 0 критических | не заменяет тест пользователями |
| CI pass rate | GitHub Actions | 100% main | аппаратные тесты отдельно |

## 28. Критерии приемки

- Без соединения аппаратные действия disabled.
- Пользователь всегда видит порт, Ready, ошибку и статус телеметрии.
- Default-значения явно не считаются прочитанными.
- Изменённая строка и общий счётчик видимы.
- Сервер передаёт в Modbus только dirty-объекты.
- При успехе очищаются только фактически переданные dirty-флаги.
- При ошибке нет ложного сообщения о полном успехе.
- Полный цикл — главный CTA раздела программ.
- Ручной сервис и PLC reset отделены; destructive actions подтверждаются.
- Навигация доступна при ширине 320 px; таблицы не превращены в карточки.
- JavaScript проходит syntax check, HTML не имеет duplicate IDs, Go проходит fmt/vet/test в CI.
- Windows build публикуется как workflow artifact.

## 29. Неподтвержденные гипотезы

1. Лаборанту нужен отдельный read-only режим, а не только дисциплина использования.  
2. Полный цикл является наиболее частым запуском.  
3. Координаты обычно меняются по одной/нескольким позициям, поэтому dirty-only существенно сокращает время.  
4. Мобильный интерфейс нужен прежде всего для диагностики, не для полной калибровки.  
5. После записи требуется обязательное автоматическое повторное чтение.  
6. Для аудита медицинского оборудования потребуется долговременный неизменяемый журнал действий.  
7. Термины «селектор», «налив, мл×10» и «Ready» однозначны для всех целевых ролей.

Проверять гипотезы следует интервью и usability-тестом до добавления крупных функций. Аппаратные последствия команд, диапазоны и время операций необходимо подтвердить на реальном ONEPAP.24.
